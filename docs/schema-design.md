# Database Schema Redesign — Design Notes

**Status: implemented and complete.** This documents the target schema, the two implementation paths discussed, and the real migration that carried them out - kept as the historical record, not a live plan; see this document's own closing line for confirmation. `crm_state` itself no longer exists (see CLAUDE.md).

## Why

The current `crm_state` table is a single EAV/blob table: rows keyed by `(kind, item_key)` where `value` is often the *entire* CRM dataset serialized as one JSON blob (`crmDataset::current`), plus override rows for mailing/component status and reviewed exceptions. No foreign keys, no real queryability, no per-entity history. This doc replaces that with a normalized relational schema.

## Decided Entities

### `subscribers`
The paying account holder, identified primarily by email. One subscriber can have multiple subscriptions.
- `id`, `email`, `name`, `created_at`

### `subscriptions`
One subscription = one character + one recipient. A subscriber can have multiple subscriptions (e.g. a second character, or a different recipient), but each individual subscription has exactly one recipient — recipients are **not** a separate reusable entity (see Decisions below).
- `id`, `subscriber_id` (FK), `character`, `term_type` (month-to-month / 6mo / 12mo), `status`, `started_at`, `total_letters_expected` (2 / 12 / 24)
- Recipient fields, inlined (current/latest known address — used as the default when generating new mailings): `recipient_name`, `address_line1`, `address_line2`, `city`, `state`, `zip`

### `orders`
The Squarespace-side transactional record. Month-to-month subscriptions produce a new order roughly monthly; longer terms may have just one order for the whole term.
- `id`, `subscription_id` (FK), `external_order_number` (Squarespace's), `amount`, `ordered_at`

### `mailings`
One row per actual letter-mailing event.
- `id`, `subscription_id` (FK), `letter_number`, `scheduled_date` (1st or 15th), `status`
- Recipient address fields, **snapshotted at mailing-creation time** (frozen copy of the subscription's address at that moment — never updated after creation, even if the subscription's address changes later): `recipient_name`, `address_line1`, `address_line2`, `city`, `state`, `zip`
- `staging_location_id` (FK, nullable — set once the physical item is printed and placed in a staging location, pre-mailing)

### `mailing_components`
Per-mailing parts and their individual production status.
- `id`, `mailing_id` (FK), `component_type` (envelope / letter / insert), `status` (printed / assembled / QA'd / etc.), `updated_at`

### `exceptions`
Needs-review flags. Nullable FKs rather than a polymorphic pattern, since a flag can relate to either level.
- `id`, `subscription_id` (FK, nullable), `mailing_id` (FK, nullable), `type` (bad_address / missing_date / duplicate / unusual_sequence), `reviewed` (bool), `created_at`, `reviewed_at`

### `ingestion_events`
Generic audit trail for how data entered the system — **not spreadsheet-specific**, by design (see Decisions below).
- `id`, `source` (`manual_spreadsheet` | `squarespace_sync`), `occurred_at`, `raw_payload` (jsonb, for audit/rollback), `status` (success / partial / failed), `summary`

### `staging_locations`
Physical storage location where printed items wait between printing and mailing. (Renamed from "bins" — see Decisions.)
- `id`, `label`, `notes`

## Design Decisions & Rationale

- **No separate `recipients` table.** Every subscription gets its own recipient; recipients are never reused across subscriptions. A separate table would force a mandatory join on nearly every query (printing, mailing-list generation) for no benefit. Recipient fields are inlined directly on `subscriptions`.
- **Address snapshot on `mailings`, not just `subscriptions`.** Families can move mid-subscription (e.g. month 6 of a 24-letter term). `subscriptions` holds the *current* address (used as the default for new mailings); `mailings` holds a *frozen* copy taken at the moment each mailing record is created, so historical letters retain the address they actually shipped to. Same pattern e-commerce systems use for order shipping addresses vs. a customer's current saved address.
- **`ingestion_events` is source-agnostic, not "spreadsheet imports."** Today the only ingestion path is manual spreadsheet upload. The Squarespace integration (currently just a TODO in Marcy/Codex's backlog — nothing designed yet) would be a second ingestion source feeding the same normalized tables. One audit table covers both, present and future, rather than needing a separate mechanism built later.
- **"Bins" → `staging_locations`.** Same real-world thing Ashley calls "the bin," renamed at the schema level to avoid ambiguity with other meanings of "bin" (trash, storage bucket, etc.) — no functional difference.
- **ORM: Drizzle** (already in use). Recommend splitting `db/schema.ts` into `db/schema/` with one file per entity (`subscribers.ts`, `subscriptions.ts`, `mailings.ts`, etc.), using Drizzle's `relations()` helper alongside table defs for typed relational queries (`db.query.subscriptions.findMany({ with: { mailings: true } })`) instead of manual joins.

## Open Items (not decided)

- Exact column types/lengths/constraints — not finalized at the field level.
- Squarespace integration shape — nothing designed; when that work resumes, check whether Marcy/Codex have already drafted a webhook/sync payload shape before finalizing `ingestion_events` and `orders` details.

## Implementation Path — Two Options

**Option A (recommended starting point): schema only.** Define the Drizzle tables above, generate the migration, get them created in Postgres. `crm_state` keeps working exactly as today — nothing reads from or writes to the new tables yet. Low-risk, independently verifiable.

**Option B: full cutover.** Everything in A, plus rewriting the import logic (spreadsheet upload currently overwrites one JSON blob — would need to become real inserts/updates across the normalized tables) and rewriting `/api/shared-state`'s GET to reassemble the same JSON shape `app.js` expects, by querying the new tables. This is a real rewrite of the core data-access layer — application/business logic, not infrastructure, and meaningfully bigger than anything done so far in this migration.

Decision when this resumes: do A first, treat B as a distinct, separately-scoped follow-up (possibly for Marcy/Codex once the target schema already exists and is proven).

## Option B, Phase 1 — Dual-Write Notes

The module referenced throughout this section as `lib/dual-write.ts` was later renamed to `lib/write-to-tables.ts`, once `crm_state` was dropped and there was no longer a second write for "dual" to mean anything - see git history. References below have been updated to the current path; the name "dual-write" in the prose describes what it was called and did at the time.

Phase 1 (superseded by Phase 2 below, kept here for history) shadow-wrote app.js's existing payloads into the normalized tables alongside the real `crm_state` blob write (see `lib/write-to-tables.ts`, wired into `app/api/shared-state/route.ts`'s POST handler). Nothing read from the normalized tables yet — this was validation only, so the blob stayed the complete, authoritative copy and a dual-write failure never blocked or failed the primary write. Building this surfaced several places where app.js's real data doesn't cleanly fit the schema above. Each is a deliberate, documented choice, not an oversight:

- **`letter_number`, `orders.ordered_at`, `subscriptions.started_at` are nullable**, not NOT NULL as originally defined. Real spreadsheet rows can lack a letter number or an original order date, app.js itself never flags either as bad data, and there's no honest fallback value that wouldn't misrepresent real data (0/1 for a letter number, a fabricated timestamp for a date). Migration `0002_last_sister_grimm.sql`.
- **Address is stored as one opaque blob in `address_line1`**; `address_line2`/`city`/`state`/`zip` are never populated. app.js's `splitNameAddress()` produces a single comma-joined string, not structured fields — there is no reliable way to split it into components without guessing (apartment numbers, multi-line addresses, and unusual formats are exactly where a naive parser would guess wrong). Real structured decomposition is a separate future project, ideally fed by actually-structured data (e.g. discrete address fields from a Squarespace integration) rather than reverse-engineered from a free-text blob that was never structured to begin with.
- **`subscriptions.total_letters_expected`** is derived from `plan` via the same mapping app.js's own `plannedLetterCount()` uses (`app/crm/legacy-app.js`): Month-to-month → 2, 6-month → 12, 12-month → 24, One-time → 1 (One-time is a real business category, not bad data, and 1 is `plannedLetterCount`'s own value for it — not an invented number). A subscription whose plan is `"Needs Review"` or otherwise unrecognized is **skipped** (not written) rather than guessing a letter count — app.js's own `spreadsheetExceptionReasons()` already flags that row as broken via the `exceptions` array, so the shadow table doesn't need to represent it; the blob remains complete and authoritative regardless.
- **A mailing with no ship date is skipped** the same way, for the same reason: app.js's own exceptions mechanism already flags `"Missing ship date"` as broken data, so this isn't a new error category — it's the schema honoring one app.js already has.
- **`orders.subscription_id` is derived, not sourced directly** — app.js's order objects carry `subscriberId`, not `subscriptionId` (a subscriber can have multiple subscriptions/characters). The dual-write derives it from the first mailing row that produced that `orderId`, mirroring the same first-occurrence-wins pattern `buildSeedFromSpreadsheet` already uses for every other id→object Map. If a single order number ever legitimately spanned two different subscriptions, only the first-seen association would be captured; this hasn't been observed and isn't guarded against.
- **`exceptions.type` stores app.js's raw joined `reason` string** (e.g. `"Missing ship date; Missing email"`), not the `bad_address`/`missing_date`/`duplicate`/`unusual_sequence` categories sketched earlier in this doc. Those categories and app.js's actual reason strings don't correspond, and collapsing app.js's more granular reasons into that four-value taxonomy would just be a different kind of guess. Revisiting `type` as a real normalized category is real future work, worth doing at Option B's actual cutover — not now.
- **`mailings.id` is a derived stable key, not app.js's own generated `mailingId`.** app.js builds `mailingId` from `slug(`${orderId}-${recipientId}-${character}-${letterNumber||sourceRow}`).slice(0, 34)` — and the 34-character truncation routinely cuts off before ever reaching the trailing `letterNumber`/`sourceRow` differentiator, because `recipientId` alone can already be up to 26 characters. In practice this means **a Month-to-month subscriber's two letters under the same order — the single most common subscription pattern (see CLAUDE.md) — generate the identical `mailingId`.** app.js itself never notices, because it never deduplicates mailings by `mailingId` alone (they're pushed into a plain array), and its own override system already works around this by keying on `mailingKey` = `mailingId::sourceRow` instead. But a normalized table's primary key has to be one real, unique value per row, so reusing bare `mailingId` as `mailings.id` silently collapsed distinct mailings into one row. Fixed by deriving `mailings.id` server-side instead, from real business fields that don't get truncated away: `${orderId}::${character}::${letterNumber}` (`letterNumber` as empty string if absent). These fields are stable across re-imports (unlike `sourceRow`, see below), so this doesn't trade the collision for a reordering bug. If two mailings under the same order+character genuinely both lack a `letterNumber`, that's real, irreducible ambiguity in the source data — both are skipped and logged rather than assigning either of them a guessed identity.
- **`mailings.app_mailing_id` and `mailings.last_source_row` are matching aids, not identity.** An incoming `mailingStatus`/`componentStatus` override carries app.js's original `mailingId` + `sourceRow` (from `mailingKey`/`componentKey`), not the new stable `id` above — so those two columns exist purely to let the dual-write look the row back up. `sourceRow` is a spreadsheet row *position*, not a stable identifier: it's `index + 2` in whatever file was most recently uploaded (`buildSeedFromSpreadsheet`, `app/crm/legacy-app.js`), and shifts if rows are added, removed, or reordered between imports. `last_source_row` is overwritten on every import with whatever `sourceRow` that mailing had *this time* — verified directly (import, note the values, re-import with rows reordered, confirm they update rather than staying stale). Matching an override requires an exact `(app_mailing_id, last_source_row)` match; zero or multiple hits is skip-and-log, e.g. if the database has since been re-imported with different row positions than whatever the browser currently has loaded.
- **`reviewedException` override keys are matched by joining `exceptions.mailing_id` → `mailings.app_mailing_id`, plus `exceptions.type` == the key's `reason` segment** (an exact match, since this module always writes `type` as that same raw reason string — see above). The key app.js generates (`exceptionReviewKey`, `app/crm/legacy-app.js`) also encodes `subscriberId` and `shipDate`, but the `exceptions` table has no columns for either to cross-check against — this is a schema limit, not a shortcut. Subscription-only fallback exceptions (see below) are never reachable this way, since the join requires a non-null `mailing_id`. If Option B's real cutover needs the key to be fully verifiable, that's the point to consider adding a dedicated snapshot column.
  **Update, post-cutover:** closed. `exceptions.review_key_subscriber_id`/`exceptions.review_key_ship_date` (`db/schema/exceptions.ts`) now snapshot the key's remaining two segments on every import (`writeImport()`, `lib/write-to-tables.ts`), and `writeReviewedException()` cross-checks all four of `mailingId`/`subscriberId`/`reason`/`shipDate` against stored columns, not two. The subscription-only-fallback limitation described above is unchanged and still real. See the audit-log task this was closed alongside, and `tests/audit-events.e2e.test.mjs` for the tests proving a key differing only in `subscriberId` or `shipDate` is correctly rejected.
- **Exceptions whose mailing was skipped** (missing ship date, or an ambiguous stable id) fall back to `subscription_id`-only linkage when the subscription itself was written; if neither the mailing nor the subscription resolved, the exception is skipped and logged rather than written orphaned with both FKs null (an orphaned row could never be matched by a `reviewedException` override anyway, since matching depends on `mailing_id`). Reviewed-state is **not** preserved across re-imports for this subscription-only fallback case (it's cleared and reinserted each import) — only the common `mailing_id`-backed case preserves `reviewed`/`reviewed_at` across imports.
- **`lib/domain/keys.ts`** (path as of the app.js decomposition's step 3b relocation - referenced throughout this section by its Phase 1-era path, `lib/keys.ts`, which no longer exists; only the path is corrected here, not the behavior described) is the tested, canonical spec for `mailingKey`/`componentKey`/`exceptionReviewKey` used by the server-side matcher. app.js doesn't import it — even though `app/crm/legacy-app.js` is a real ES module now (the app.js → ESM move, see CLAUDE.md §9), the two are deliberately kept as separate, tested-in-sync copies rather than importing this directly; its own inline copies remain the real client-side source of truth. `tests/keys.test.mjs` verifies the two stay identical by running the actual `app/crm/legacy-app.js` in a sandbox and diffing its real output against `lib/domain/keys.ts` for the same sample data, not just comparing the two implementations by eye. `lib/write-to-tables.ts`'s own `stableMailingId()` derivation is deliberately kept separate from `lib/domain/keys.ts` - it isn't app.js behavior being mirrored, it's new server-only logic invented to work around a real gap in app.js's own ID scheme.

## Option B, Phase 2 — Read Path, Schema Gap Closure, Load-Bearing Write

Picked back up once Phase 1 had been running long enough to trust. Four steps, done in this order (the sequencing itself was a deliberate correction — see the third bullet):

1. **`lib/build-dataset-from-tables.ts`: the first reader.** Reconstructs app.js's full `crmDataset` shape (`buildSeedFromSpreadsheet`'s output) by querying the normalized tables directly, instead of reading the `crm_state` JSON blob. One small builder function per output entity (`buildSubscribers`/`buildRecipients`/`buildOrders`/`buildSubscriptions`/`buildMailings`/`buildExceptions`/`buildSummary`), composed by `buildDatasetFromRows`/`buildDatasetFromTables`. Deliberately **not** wired into `app/api/shared-state/route.ts`'s GET handler yet - a correctness foundation, proven with tests before anything reads from it live. `overdue`/`dueNext14Days`/`summary.asOf` are computed *live* here (query-time "now"), unlike app.js's client-side computation, which freezes them at import time - a deliberate improvement once this is eventually wired in.
2. **`tests/build-dataset-from-tables.e2e.test.mjs`: proof, not assumption.** Real spreadsheet → real sandboxed `app/crm/legacy-app.js` → real `dualWriteImport()` into a real local Postgres → real `buildDatasetFromTables()` → deep field-by-field diff of every record in every array. Every discrepancy the diff finds is checked against an explicit `ALLOWED_DISCREPANCIES` allowlist, each entry individually root-caused against the real 1,218-row test file; anything outside it fails the test. This is what actually found the `mailings.active` gap below - not a design review, an empirical diff against real data.
3. **Closed the schema gaps that diff surfaced, before promoting the write path** (originally planned the other way around - reordered on review: once `crm_state` is retired, an unclosed gap becomes permanently unrecoverable instead of merely "not yet closed," so schema-complete has to come before write-path-authoritative). Three additive columns, one migration (`drizzle/0004_married_cloak.sql`):
   - **`mailings.active`** (boolean, not null) - the one gap with real correctness impact. It used to be sourced from the mailing's subscription's single `status` column; app.js actually computes it *per mailing row*, from that row's own "Active?" cell, and a subscription's rows can genuinely disagree (7 of 1,218 mailings in the real test file). Named `active` rather than reusing `status` to avoid colliding with the unrelated production-status `status` column already on `mailings`.
   - **`mailings.notes`** (text, nullable) - free-text operational notes, previously not persisted at all.
   - **`subscriptions.ended_at`** (timestamp, nullable) - subscription end date, previously not persisted at all.
   - `lib/write-to-tables.ts` and `lib/build-dataset-from-tables.ts` updated together; e2e discrepancy count dropped from 865 to 72 as a direct result (mailings field-mismatches specifically: 729 → 0). The 72 remaining are the same two genuine, already-documented causes (2 subscriptions with an unrecognized Plan cell; the one real spreadsheet duplicate at `ORD-2858`) plus two deliberate design choices (`subscribers[].status`/`firstOrderDate` use well-defined aggregates instead of app.js's row-order-first-wins artifact; array tie-break ordering can differ since the normalized schema doesn't preserve cross-entity spreadsheet row order) - see `lib/build-dataset-from-tables.ts`'s module comment for the full, current list of what's still a known gap.
4. **Made the write path load-bearing and transactional.** `app/api/shared-state/route.ts`'s POST handler now wraps the `crm_state` insert and the dual-write dispatch in one `db.transaction()` - both succeed or both roll back. Every `lib/write-to-tables.ts` function now takes the shared `db`/`tx` handle (see its exported `Db` type) instead of calling `getDb()` internally, and no longer swallows genuinely unexpected errors in an outer try/catch - a real failure (bad connection, constraint violation, a bug) now propagates and fails the request, matching the primary write's existing behavior. This is a deliberate reversal of Phase 1's "never blocks or fails the primary write" design: dual-write is trusted now, precisely because Phase 1 ran long enough, and Phase 2 step 3 closed the known gaps first. The per-record skip-and-log logic throughout `lib/write-to-tables.ts` (e.g. "skipping subscription, unrecognized plan") is unchanged and still doesn't throw - those are expected, legitimate business outcomes (app.js's own exceptions mechanism already flags the same rows as broken), not errors.

5. **Wired `buildDatasetFromTables` into the GET handler.** `app/api/shared-state/route.ts`'s GET no longer reads `crmDataset::current` from `crm_state` for `dataset` - it calls `buildDatasetFromTables()` directly. `crm_state` itself is untouched (POST still writes it, the table isn't dropped) - this is only GET switching readers, so the blob write stays a safety net until this is live and trusted. Two gaps had to be closed for this specific wiring, both in new `lib/build-overrides-from-tables.ts` (same pure-function-plus-thin-fetch-wrapper shape as `lib/build-dataset-from-tables.ts`, both reusing `lib/domain/keys.ts`'s real `componentKey()`/`exceptionReviewKey()` rather than re-deriving either format):
   - **`componentOverrides`** has no equivalent in the `Dataset` shape at all (`mailing_components` isn't one of its seven entities) - `fetchComponentOverrides()` queries it separately and keys the result the same way `app/crm/legacy-app.js`'s `componentStatus()` already expects, so envelope/letter/artifact/insert/qa statuses don't silently revert to their defaults.
   - **`reviewed`** exception keys: `buildExceptions()` deliberately returns every exception regardless of `exceptions.reviewed` (`summary.exceptionCount` needs to keep counting reviewed ones too - unchanged, not touched by this step). `fetchReviewedExceptionKeys()` queries `exceptions.reviewed = true` separately and computes each one's key via `exceptionReviewKey()`, so `app/crm/legacy-app.js`'s existing client-side `isExceptionReviewed()`/`activeExceptions()` filtering keeps hiding them exactly like it did when GET read the blob. Only emits a key when the underlying mailing/subscriber/ship-date are all resolvable - inherits the same subscription-only-fallback gap `buildExceptions()` already has (see `lib/build-dataset-from-tables.ts`'s module comment); a reviewed exception in that narrow case can't be reconstructed and stays unreviewed after a reconstruction-backed GET.
   - **`statusOverrides` is now always `{}`** - not a gap. `buildMailings()` already reads each mailing's live `status` directly from the `mailings` table, which `dualWriteMailingStatus` writes to directly and (as of step 4) is load-bearing - there's nothing left for a separate override map to contribute, and `app/crm/legacy-app.js`'s `effectiveMailing()` already falls through to `mailing.status` when there's no override.

6. **Stopped writing `crm_state`.** GET's new read path (step 5) was live-verified in the running app, not just covered by tests, which unblocked this. `app/api/shared-state/route.ts`'s POST handler no longer inserts/updates a `crm_state` row at all - the `crmDataset` case's `JSON.parse(value)` (to extract `seed` for `dualWriteImport`) reads directly from the POST request body, so removing the insert doesn't affect it. The dual-write dispatch still runs inside `db.transaction()`, now the only thing in it. **The `crm_state` table itself is untouched and not dropped** - deliberately kept around, unwritten, as a free rollback path, the same reasoning Phase 2 step 3 (schema-gap closure before making the write load-bearing) already used: an unclosed gap - or here, a bad cutover - is recoverable right up until the safety net is actually removed, and not after. `tests/write-to-tables-transactional.e2e.test.mjs`'s two tests were rewritten to match: the rollback test now asserts on normalized-table row counts (`subscribers`/`subscriptions`) instead of a `crm_state` row, and the soft-skip test asserts on the POST response (`200`/`{ ok: true }`) instead of a leftover `crm_state` row - a soft skip writes nothing to any table, so a row-based check there was never actually proving the transaction committed, only that a row existed from a previous write. `tests/shared-state-get.e2e.test.mjs` gained a dedicated test proving a full import -> reviewedException -> componentStatus -> mailingStatus -> GET round trip works correctly with `crm_state` never populated at all (not merely truncated first) - distinct from "empty because truncated," which wouldn't catch a hidden read dependency masked by a stale row.

7. **Dropped the `crm_state` table.** All app data at this point is disposable test data (freely re-importable from the source spreadsheet - see CLAUDE.md), so the usual "wait and build trust live" gap between steps was skipped deliberately here on that basis, not because the sequencing reasoning changed. `db/schema.ts` (which held only `crmState`) is deleted; `db/index.ts` no longer passes a `schema` object to `drizzle()` (nothing uses the relational query API it enabled); `drizzle.config.ts`'s schema list no longer includes it. Migration `drizzle/0005_robust_hobgoblin.sql` is a single `DROP TABLE "crm_state" CASCADE` (no incoming FKs to cascade through - CASCADE is a no-op safety net, not load-bearing here). `tests/write-to-tables-transactional.e2e.test.mjs` and `tests/shared-state-get.e2e.test.mjs` had `crm_state` removed from their `TRUNCATE` lists; `shared-state-get`'s dedicated "GET works with crm_state never populated" test was removed outright rather than adapted - once the table doesn't exist, there's nothing left for that test to distinguish (no table to be "populated" or not).

This is Option B's real cutover, complete: the normalized tables in `db/schema/` are the only source of truth for `/api/shared-state`, both directions. Nothing "remaining" here - the entire migration described in this document, from schema design through dual-write through the read-path cutover to blob removal, is done.
